① ping 8.8.8.8은 되지만 ping google.com은 호스트를 찾을 수 없다.

숫자로 된 IP 주소로는 통신이 되지만 도메인 이름으로는 통신이 되지 않는다. 따라서 도메인 이름을 IP 주소로 변환하는 DNS에 문제가 있을 가능성이 크다. IP 통신은 가능하므로 DNS 설정이나 이름 해석 과정부터 확인한다.

② 기본 게이트웨이에 ping해도 요청 시간이 만료된다.

기본 게이트웨이는 내 PC가 다른 네트워크로 통신할 때 거치는 장치다. 게이트웨이까지 응답이 없으므로 케이블이나 Wi-Fi 연결, 네트워크 어댑터, 공유기 등 1~3계층과 관련된 문제를 의심한다. 다만 게이트웨이가 ICMP 응답을 차단하는 경우도 있으므로 이것만으로 원인을 확정할 수는 없다.

③ ping은 모두 되지만 특정 웹 사이트만 열리지 않는다.

IP 연결은 가능하지만 특정 웹 사이트만 열리지 않으므로 4계층 이상의 문제를 의심한다. 해당 서버의 웹 서비스 상태, HTTPS 포트(443), 방화벽, 브라우저 설정 등을 확인한다. ping 성공만으로 웹 서비스까지 정상이라고 판단할 수는 없다.

-이 교시에서 새로 알게 된 것: Wireshark로 내 PC와 외부 서버 사이에서 오가는 패킷을 캡처하고, Source와 Destination의 IP 주소 및 포트 번호를 통해 통신 방향을 구분하는 방법을 배웠다. 또한 Ethernet II, Internet Protocol Version 4, Transmission Control Protocol의 상세 정보를 펼쳐 MAC 주소, IP 주소, TTL, 포트 번호와 TCP Flags를 확인했다. 표시 필터 dns, udp, tcp.port == 443을 사용하면 필요한 패킷만 화면에 표시할 수 있으며, 필터를 적용해도 전체 Packets 수는 유지되고 Displayed 수만 바뀐다는 점을 이해했다.

### 1. 연결이 열리는 순간 — 3-way handshake

세 줄의 Source → Destination 과 Info:

104.20.23.154 → 192.168.100.134 — 80 → 56741 [SYN, ACK]

- 답:TCP 연결 설정이 완료되어 두 컴퓨터가 데이터를 주고받을 수 있는 상태가 된다.

### 2. 패킷 하나를 열어 본 값 — 6-3

- 이것이 보안에서 문제가 되는 이유는 무엇인가요?
  - 답: HTTP는 통신 내용을 암호화하지 않기 때문에 네트워크 경로에서 패킷을 볼 수 있는 사람이 요청 경로와 쿼리 문자열을 읽을 수 있다. 실제 서비스에서 민감한 정보가 노출될 수 있으므로 HTTPS를 사용해 통신 내용을 암호화하는 것이 중요하다.
