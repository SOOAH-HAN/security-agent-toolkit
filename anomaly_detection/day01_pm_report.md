## 5교시 · 접속 로그 한 줄을 조각으로 읽기

### 문제 5-1 · 접속 로그 한 줄에서 주소 · 방법 · 경로 · 상태 코드 꺼내기

- (가) 실행한 출력 전체를 붙여 넣고, 읽기 성공한 줄과 읽기 실패한 줄이 각각 몇 줄인지, 읽기 실패한 줄이 어떤 줄인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 읽기 성공 · 읽기 실패 줄 수 ③ 읽기 실패한 줄이 어떤 줄인지
  - 답:

```
--- 단계 1: 로그 파일 읽기 - 전체 30 줄
읽기 성공 28 줄 · 읽기 실패 2 줄
--- 단계 2: 로그 첫 3줄을 읽은 결과
{'ip': '198.51.100.21', 'method': 'GET', 'path': '/', 'status': 200}
{'ip': '198.51.100.21', 'method': 'GET', 'path': '/static/app.css', 'status': 200}
{'ip': '198.51.100.34', 'method': 'GET', 'path': '/login', 'status': 200}
--- 단계 3: 값이 덧붙은 요청 (경로에 ? 포함)
192.0.2.15 /board?page=2
192.0.2.15 /search?q=network
```
읽기 성공: 28줄
읽기 실패: 2줄
198.51.100.21 - - [02/Nov/2026:09:31:40 +0900] "GET /board/5 HTTP/1.1

-

첫 번째 줄은 요청을 감싸는 큰따옴표가 완성되지 않은 잘린 로그입니다. 두 번째 줄은 로그 형식에 맞지 않는 내용입니다. 두 줄 모두 큰따옴표가 두 개보다 적어 파싱에 실패했습니다.

- (나) 🔍 로그 한 줄만 보고 알 수 있는 것과 알 수 없는 것을 구분해 적어 주세요. 예를 들어 203.0.113.50 의 요청에서 접속자가 누구인지, 로그인에 성공했는지는 알 수 있나요?
  - 쓸 내용: ① 로그 한 줄만 보고 알 수 있는 것 ② 알 수 없는 것 ③ 203.0.113.50 의 요청으로 본 예
  - 답:
로그 한 줄을 보면 요청을 보낸 IP 주소, 요청 방법(GET·POST), 요청 경로, 상태 코드 등을 알 수 있습니다. 이를 통해 어떤 주소에서 어떤 경로로 요청했으며 서버가 어떤 결과를 응답했는지 확인할 수 있습니다.

하지만 IP 주소만으로 실제 접속자가 누구인지는 알 수 없습니다. 또한 상태 코드만으로 실제 사용자의 신원이나 이후 행동까지 확정할 수는 없습니다.

예를 들어 203.0.113.50은 /login 경로에 POST 요청을 여러 번 보냈으며, 처음에는 401 상태 코드가 5회 기록되었습니다. 이후 여섯 번째 POST 요청에서는 302 상태 코드가 기록되었습니다. 수업 자료에 따르면 로그인 성공 시 302 응답이 자주 발생하므로 로그인에 성공했을 가능성이 있습니다. 하지만 로그에 계정 정보가 없으므로 실제 접속자가 누구인지는 알 수 없고, 302 응답만으로 로그인 성공을 확정할 수도 없습니다. 이후 /admin과 /admin/users 요청에서는 403 상태 코드가 기록되어 해당 경로에 대한 접근이 허용되지 않았다는 점을 확인할 수 있습니다.

- (다) 🔍 404 가 한 번 난 요청과, 같은 주소에서 `/.env` · `/wp-login.php` · `/phpmyadmin` 이 연달아 404 가 난 요청은 같은 일일까요? 샘플 로그에서 두 경우를 찾아 어떻게 다른지, 왜 한 줄만 봐서는 판단하기 어려운지 적어 주세요.
  - 쓸 내용: ① 한 번의 404 와 연달아 난 404 의 차이 ② 한 줄만 봐서는 판단하기 어려운 이유
  - 답:
한 번의 404는 사용자가 존재하지 않는 페이지를 잘못 요청했거나 삭제된 페이지에 접근한 상황일 수 있습니다. 샘플 로그에서는 198.51.100.21 주소가 09:22:30에 /board/99를 요청했고, 404 상태 코드가 한 번 발생했습니다.

반면 198.51.100.90 주소에서는 09:20:10부터 09:20:12까지 /.env, /wp-login.php, /phpmyadmin 경로를 1초 간격으로 연달아 요청했고, 모두 404 상태 코드가 발생했습니다. 이러한 요청은 환경 설정 파일이나 관리자 페이지가 존재하는지 확인하려는 자동화된 탐색 또는 스캔일 가능성이 있습니다.

한 줄의 404 기록만으로는 단순한 주소 입력 실수인지 의도적인 탐색인지 판단하기 어렵습니다. 따라서 같은 IP 주소에서 어떤 경로를 반복적으로 요청했는지, 요청 간격은 어떠했는지 등 여러 로그를 함께 살펴봐야 상황을 더 정확하게 판단할 수 있습니다.

## 6교시 · 이상 징후 가르기와 SIEM(심)

### 문제 6-1 · 읽은 로그 줄을 정상 · 오류 · 의심으로 가르기

- (가) 실행한 출력 전체를 붙여 넣고, 분류별 요청 수와, 의심으로 분류한 요청 중 같은 주소에서 반복된 것을 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 분류별 요청 수 ③ 같은 주소에서 반복된 의심 요청
  - 답:

```
--- 단계 1: 분류별 요청 수 - 전체 28 개
정상 15 · 오류 5 · 의심 8
--- 단계 2: 의심으로 분류한 요청
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 POST /login 401
203.0.113.50 GET /admin 403
203.0.113.50 GET /admin/users 403
198.51.100.77 GET /admin 403
--- 단계 3: 오류로 분류한 요청
198.51.100.90 GET /.env 404
198.51.100.90 GET /wp-login.php 404
198.51.100.90 GET /phpmyadmin 404
198.51.100.21 GET /board/99 404
198.51.100.34 GET /report 500
```
분류별 요청 수: 정상 15개, 오류 5개, 의심 8개입니다.

203.0.113.50 주소의 POST /login 요청은 401 상태 코드로 5회 반복됐고, 같은 주소의 /admin과 /admin/users 요청도 각각 403 상태 코드로 기록됐습니다. 198.51.100.77 주소의 /admin 요청은 한 번만 의심으로 분류됐습니다.

- (나) 🔍 상태 코드와 경로만으로 분류를 정하면 놓치는 것이 있습니다. 샘플 로그에서 놓친 예를 두 가지 찾아(정상이나 오류로 분류됐지만 살펴볼 만한 요청) 왜 놓쳤는지 적어 주세요.
  - 쓸 내용: ① 놓친 예 두 가지 ② 각각 왜 놓쳤는지
  - 답:
첫째, 203.0.113.50의 POST /login 401 5회 이후에 나온 302 응답입니다. 분류 규칙상 성공 이동으로 보이는 302는 정상으로 분류되지만, 그 앞의 반복된 로그인 실패 이후 성공했을 가능성이 있어 추가로 살펴봐야 합니다. 상태 코드와 경로만 보면 401 실패 기록과 302 성공 기록 사이의 반복 패턴을 놓칩니다.

둘째, 198.51.100.90의 /.env, /wp-login.php, /phpmyadmin 요청입니다. 이 요청들은 404 오류로 분류되지만, 1초 간격으로 연속해서 서로 다른 관리·설정 경로를 확인한 것으로 보이는 탐색 행위일 수 있습니다. 한 요청씩 상태 코드와 경로만 보면 흔한 404일 뿐이고, 같은 주소의 반복과 요청 순서·시간 간격을 고려하지 않아 놓쳤습니다.

- (다) 🔍 5교시 「현업에서 SIEM(심)을 쓰는 방식 여섯 가지」 표의 방식 중에서, 보안 전담 직원이 1명뿐이고 쓰는 서비스 대부분이 클라우드에 있는 작은 회사라면 어느 방식을 고를지 이유와 함께 적어 주세요. 고르지 않은 방식 하나가 왜 맞지 않는지도 적어 주세요.
  - 쓸 내용: ① 고른 방식과 이유(로그 양 · 인력 · 데이터 위치) ② 고르지 않은 방식 하나와 맞지 않는 이유
  - 답:
보안 전담 직원이 1명이고 서비스 대부분이 클라우드에 있는 작은 회사라면 클라우드(SaaS) SIEM 방식이 적합합니다. 로그 양이 과도하게 많지 않을 가능성이 있고, 전담 인력이 1명이라 서버·스토리지·규칙 운영 부담을 직접 떠안기 어렵기 때문입니다. 서비스 대부분이 클라우드에 있으므로 클라우드에서 로그 수집과 관리를 연결하기도 상대적으로 쉽습니다.

고르지 않을 방식은 설치형 SIEM입니다. 장비를 직접 구매하고 설치한 뒤 수집·보관·고가용성·백업·규칙 관리까지 운영해야 하는데, 보안 전담 직원 1명이 감당하기에는 관리 부담이 큽니다. 이미 대부분의 서비스가 클라우드에 있다면 온프레미스 장비 중심의 설치형 방식과 데이터 위치도 맞지 않습니다.

### 마무리 · 오늘 만든 것을 깃허브에 올리기

- (가) `git status` 를 쳤을 때 `.env` 나 `.venv` 가 보였는지, 보였다면 어떻게 했는지 적어 주세요.
  - 쓸 내용: ① `.env` · `.venv` 가 보였는지 ② 보였다면 한 조치
  - 답:
현재 `git status`에서 `.env`나 `.venv`가 보이지 않았습니다.

보이지 않았으므로 별도로 삭제하거나 `.gitignore`에 추가하는 조치는 하지 않았습니다. 앞으로도 비밀 정보나 가상환경 폴더가 실수로 Git에 올라가지 않도록 `.env`와 `.venv/`를 `.gitignore`에 유지하는 것이 좋습니다.
